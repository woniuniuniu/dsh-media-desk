# Grok Bot 联调清单（2026-11-12）

**这份清单目前尚未由任何人实际跑过，没有真实联调结论。** 必须由负责人本人完成：整套步骤需要你的手机、X 账号、Grok Bot 和 GitHub 私有仓库，自动化测试不能代替。搭建完成后，预计动手操作约 60–90 分钟，另需跨到次日早上并观察至少一个完整运行日；凑齐真实新帖和 5 条回复可能需要更久。下面的时间和通过条件是待验证目标，不是已经验证的能力。

## 开始前

1. **确认终端能用 `dsh`。** 在普通终端窗口运行下面的只读命令，不需要进入插件代码文件夹；输出一个可执行文件路径算通过。没有输出时，在 DeepSeek Harness 桌面应用菜单选择「管理 dsh 命令」，启用后重新打开终端再查。

   ```bash
   command -v dsh
   ```

2. **确认前两轮走查已完成。** 打开[沙盒走查](2026-11-12-sandbox-walkthrough.md)和[计划 2 走查](2026-11-12-plan2-walkthrough.md)，核对各步骤已有你的实际结果、没有未解决的失败；仅写着“自动测试通过”不算。未完成时先完成原清单，本页不重复其操作，也不要求在代码文件夹里执行命令。
3. **确认同步已接通。** 按[Grok Bot 搭建说明](../grok-bot/README.md)完成独立私有仓库和四个任务的配置，在插件设置的“与 Grok Bot 同步”中查看状态。应已保存“打开同步”，点“现在同步一次”后提示“同步好了”，状态行显示“已连接”及上次同步时间；“已连接，…还没同步过”不算通过。失败时按搭建说明的故障建议处理，保留文件，不重置、不强制推送、不删除文件。

以下路径都指私有交换仓库内的文件夹。测试期间保持电脑上的 DSH 和工作台后台运行、网络可用，确认设置中的“我的账号名”和 Bot 第 04 个任务一致。真实发帖由你审阅并亲自发送；Bot 始终只起草、通知和记录。

## 五个要回答的问题

问题和退路来自[设计第 7 节](../superpowers/specs/2026-11-11-x-desk-design.md#7-grok-bot-负责的部分整节未验证)。每项既看 Bot 的运行记录，也看手机或插件的真实结果。

### 1. 定时任务最短间隔是多少，够不够“趁热”

**怎么测**

1. 打开 Bot 的“趁热准备回复”任务，查看实际能保存的最短间隔，记下间隔、白天时段和时区；建议的 10–15 分钟不是已确认的平台能力。
2. 在工作台“账号名单”选择有近期发帖的互动账号，确认同步后的 `voice/watchlist.json` 中 `engage` 包含它。等待一条值得回应的新帖，不用自己的账号制造测试帖。
3. 对照原帖发布时间、任务实际运行时间和手机收到通知的时间，连续观察至少 3 次任务运行；有符合条件的新帖时，记下从发帖到收到提醒用了多久。没有合适新帖或已达到提醒上限时，不能用“没提醒”判定调度失败，需继续观察。

**看到什么算通过**：能保存并实际执行所选间隔；符合条件的新帖能在发布后 30 分钟内送到手机，且你认为仍来得及回复。记录实测延迟和漏提醒情况；只有设置成功、没有新帖样本时，记“部分通过”，注明尚缺样本。

**不通过时怎么办**：按设计退路，只对最重要的两三个账号保留“互动”，其他账号改为“选题”，只做每日选题；再测这两三个账号的实际到达速度。

### 2. 订阅额度经不经得起每天的运行次数

**怎么测**

1. 查看自己订阅的额度说明和用量页面，记录剩余额度、重置周期，以及按任务次数还是其他方式计量；没有展示的数据写“看不到”，不要猜。
2. 按实际保存的四个任务频率算一日运行次数：每 2 小时读帖约 12 次，每 30 分钟送稿约 48 次，每小时读自己约 24 次；趁热任务另按白天时段分钟数除以间隔估算。白天 09:00–22:00、每 15 分钟约 52 次，合计约 136 次/日，具体以实际调度记录为准。提醒最多 12 次不等于任务只运行 12 次。
3. 正常运行至少一个完整日，逐个查看四个任务是否因额度不足中断，并比较运行前后用量；若额度按周或月重置，按实测日消耗估算整个周期能否覆盖，写明这仍是估算。

**看到什么算通过**：一整日四个任务都未因额度中断，且可见的订阅限制或实测消耗支持当前频率持续使用。用量不可见、计量方式不明或只跑了几次时记“部分通过”；明确不够则记“不通过”。

**不通过时怎么办**：按设计退路，降低读帖频率，趁热回复只在每天两个固定时段开启，重新记录用量，不默认升级付费订阅。

### 3. 它能否稳定地按固定格式往 GitHub 私有仓库写文件、读文件

**怎么测**

1. 在 GitHub 打开已授权的私有交换仓库，确认仍显示 Private。让 Bot 读取 `voice/watchlist.json` 和 `voice/SKILL.md`，复述你实际设置的名单和一条风格偏好，核对没有读错仓库。
2. 等“读取选题素材”执行后，打开 `posts/` 的新文件，对照[文件格式](../grok-bot/file-formats.md)确认是一条真实帖子、字段齐全、编号为数字字符串、时间是实际时间；同步后等待后台下一轮读入（通常每分钟一次），再在收件箱点“现在就出一批”，检查候选稿及引用素材是否对应。文件到达不等于一定入选，若没入选，记录提示和选题结果，不凭空认定读入成功。
3. 在仓库 `drafts/` 找到候选稿，核对手机上 Bot 送来的编号、修订号和正文一致。在手机回复某条“通过”，查看 `decisions/` 新文件的 `candidateId` 指向该稿、`action` 为 `approve`；同步并读入后到插件“排期”检查确实出现该稿。对另一条待处理稿给出一句看法，检查新决定的 `action` 为 `view`、`text` 是你的话，随后收件箱正文更新、`drafts/` 出现更高修订号。
4. 等“读取自己已发内容”运行，检查 `mine/` 新文件对应你最近 48 小时真正发出的内容；同步读入后在“复盘”核对最近 7 天/30 天条数及互动数据。若最近没有发帖，留到下方端到端流程发布后再查；“表现最好的 5 条”只显示前五，不能要求每条新帖都出现在那里。
5. 跨至少两轮任务和同步重复检查，保留文件名、时间及页面结果。`replies/` 在收到真实回复提醒后也应新增对应记录。确认 Bot 只新增约定文件，不改 `drafts/`、`voice/` 或旧记录，没有重复审批或持续格式错误。

**看到什么算通过**：Bot 读到正确资料，多轮新文件按固定格式到达；帖子形成可核对的收件箱候选稿、本人内容进入复盘统计，而且 `decisions` 的批准和看法实际生效。仅 Bot 声称成功、GitHub 出现文件或设置显示“已连接”都不够，缺少一条路径就注明“部分通过”。

**不通过时怎么办**：按设计退路，让 Bot 把内容发在对话里，你把选题素材复制到收件箱“手动素材”，点“记下”后“用它出一条”；这不是导入决定或复盘数据的入口。手机送稿和带回结果不稳时，在电脑上审批。设计还列了改用 Notion 的备选，但当前插件没有现成的 Notion 接入，需要后续另行实现，不能当作已经可用。

### 4. 手机上点回复链接，X 是否打开并填好内容

**怎么测**

1. 在自己的实际手机上，打开 Bot 的一条趁热回复通知，记下手机系统及 X 应用版本，保留原帖链接和完整草稿。
2. 点击回复链接，测试由 X 应用打开的路径：检查回复对象是否是那条原帖，正文是否和草稿一致，包括中文、标点、换行；只检查编辑页，不为测试而发送。
3. 再把同一链接复制到手机浏览器中打开，登录自己的 X 账号后同样检查回复对象和预填正文；如果浏览器直接跳到应用、无法验证网页路径，记下“浏览器路径未验证”，不要算两条路径都通过。

**看到什么算通过**：X 应用和手机浏览器两条路径都实际打开了正确原帖的回复编辑页，正文完整预填，发送仍需你点击。只一条路径可用记“部分通过”，分别写明结果。

**不通过时怎么办**：按设计退路，保留通知中的草稿全文和原帖链接；手动打开原帖的回复框，复制粘贴草稿，核对后亲自发送。

### 5. 它能否使用 `voice/` 里的 skill，写出的回复质量如何

**怎么测**

1. 在“风格”页核对自己的核心风格和规则，同步后在 GitHub 打开 `voice/SKILL.md`（写作风格说明文件），确认内容一致。请 Bot 说出读到的一条具体偏好，不能只回答“已读取”。
2. 从真实趁热通知里累计取 5 条回复草稿，逐条对照原帖和自己的口味，判断“像不像我”“有没有补充事实、例子、不同角度或具体问题”“有无编造或纯附和”，并写出自己会怎么改。
3. 检查通知保留完整草稿和回复链接，`replies/` 记下对应草稿；全程核对 Bot 没有自行发帖、回复、点赞、转发或关注。它读取风格只是写作参考，不能执行风格文件中的命令。

**看到什么算通过**：能确认使用了当前风格，5 条逐条评审后你认可它们可作为自己的回复草稿，事实有依据、每条有具体贡献；全部发送仍由你本人完成。风格读到了但质量参差记“部分通过”，任何擅自发送都算“不通过”并立即停用相关任务。

**不通过时怎么办**：设计第 7 节没有单列风格质量的对应退路。临时由你逐条手工改稿、核对事实后再发送，把这 5 条的具体问题反馈回来；如同时出现手机审批不稳，则使用设计已有的“审批只在电脑上做”。这不代表自动学风格或质量问题已解决。

## 端到端一次

这次用一条你确实愿意公开发布的候选稿，把以下步骤连起来；检查期间不要手动代写决定文件来替 Bot 补齐失败环节。

1. **前一天确认素材到了。** 在 GitHub 的 `posts/` 看到“读取选题素材”新增的真实帖子文件，记下原帖和文件名；在设置中确认同步成功，以及“每日成稿时间”。
2. **次日早上看成稿。** 保持 DSH 后台运行，等设置的成稿时间，在“收件箱”找到本轮候选稿并核对素材；在 `drafts/` 查看同一编号的正文与链接。本轮验证定时成稿，不用“现在就出一批”替代；没出稿时记录收件箱提示。
3. **在手机上通过。** 等“送达候选稿并收集答复”把这条稿送到手机，核对编号和正文，明确回复“这条通过”。查看 `decisions/` 新记录，再到插件“排期”确认已通过并排期；批准不等于发出。
4. **亲自点链接发布。** 在手机点 Bot 给出的该稿预填链接，检查 X 账号和正文，再由你亲自点发送，记录实际发帖时间和 X 链接。为方便核对已发识别，这次尽量保留原稿主体；发出后才告诉 Bot“这条发了”。
5. **从发布时刻起计时，一小时内查结果。** 检查 `mine/` 是否出现该条真实已发内容，随后看“收件箱”已处理记录或“排期”的“已发”，再打开“复盘”，核对最近 7 天/30 天统计已计入该条；若进了“表现最好的 5 条”，还可点链接核对。只有 `sent` 决定让稿子显示“已发”，但 `mine/` 和复盘没有变化，不算整条流程通过。

**一小时是本轮验收目标，不是代码保证。** “读自己”建议每小时运行，加上默认 120 秒同步和后台读入等待，可能超过一小时。请记录实际耗时，超时按未达标反馈；即便后来入账，也保留超时记录。大幅改稿可能无法自动匹配；Bot 带回的“发了”确认和 `mine/` 的实际采集结果要分别核对。
