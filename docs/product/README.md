# 产品背景与演变

X 工作台是一个 DeepSeek Harness（DSH，桌面 AI 工具）插件，给一个人运营一个 X 账号使用。程序准备选题、草稿、风格和复盘，负责人在收件箱里判断、补充自己的看法，再亲自发送；目标是让有全职工作、刚开始创作的人用碎片时间持续经营账号。

## 从多平台工作台到 X 收件箱

2026 年 11 月 11–12 日的规划从负责人自己的分叉 `YjAdair/dsh-heimao-media-desk` 开始，上游是 MIT 许可的 `woniuniuniu/dsh-media-desk`，提供灵感墙、视频脚本、封面、分镜、排期、复盘和风格。负责人同时提出 BlueV（bluev.fun）作为参考：爆款雷达、AI 改写、海报、定时发布和 Chrome 扩展，核心是发现正在传播的内容，再改写成自己的内容。

负责人的现实条件决定了范围：一个人、一个 X 账号，有全职工作，自己写过的内容少，尚未形成稳定口吻；希望快速涨粉、尽量自动化，每天能在手机上分几次投入约十分钟，有一台白天常开的电脑。于是选择硬分叉，只做 X，去掉另外八个平台与视频分镜，不再持续合并上游。产品也从需要人操作的工作台收窄为收件箱：程序把事情准备到最后一步，人只判断和发送。原设计写的是每天 15–20 分钟、每周另花约一小时处理长文；它是当时的设计预算，并非已经验证能满足“约十分钟”的实际效果。

内容策略以回复头部账号为新账号的主要增长手段，短帖与引用帖保持活跃，每周一篇长文；推文串等有数据再议。自动点赞、回复、转发、关注和发帖均不做，由人通过预填链接亲自发送。写作采用“谁在说话”的核心风格与“这类内容怎么写”的内容类型两层，初始类型为产品、模型、技术底层、社会；先借 `khazix-writer` 搭起风格，再随着自己的内容积累转向自己的口吻。自己的观点和经历必须由人补充，程序不能编造第一手经历。

## 从数据接口到 Grok Bot 与文件交换

负责人拒绝原分叉使用的 Monid 等第三方抓取服务，也不采用付费 X 开发者 API，改用已经订阅的常驻云端代理 Grok Bot。由于程序无法直接调用 Grok Bot，分工变成：Grok Bot 读 X、趁热起草回复并联系手机上的负责人；插件负责选题、成稿、风格、学习与复盘。

双方通过一个交换文件夹里的固定格式 JSON 文件通信，再用 GitHub 私有仓库同步。同步默认关闭，需负责人明确开启；插件本身只认本地文件，因此没有 Grok Bot 时，仍能用示例文件或手动粘贴完成本地流程。云端连接、定时任务、手机预填链接和回复质量仍需真实联调，不能由本地测试替代。

## 三份计划与实现中的纠正

实现依次完成底座与发帖线、学习与长文、交换同步与 Grok Bot 指令。每项任务经过实现、独立审阅和修复，每份计划结束再做整分支审阅和一轮集中修复；从计划 2 中途开始引入 OpenAI Codex（`gpt-6-astra`）执行，随后默认交给 Codex。Claude 负责写清边界、裁定、重新跑测试与构建、检查范围、提交及组织独立审阅。

审阅改变了几个关键设计：认出“已发”要宁缺毋滥；手机答复必须记住是否处理过，不能因重新克隆就再次改稿；回复使用率必须按同一批回复草稿算；同步必须隔离代码仓库、保护本机处理记录并限制提交范围。具体规则、原因和代价保存在 [决策记录](decisions.md)，设计末尾列出实现变更；三份计划保留原来的任务内容和复选框，作为实施历史，不能用其中尚未勾选的框判断当前完成度。计划 1 拟定的走查文件日期为 2026-11-11，实际交付是 [2026-11-12 的走查记录](../spikes/2026-11-12-sandbox-walkthrough.md)，查阅时以本页索引为准。

截至 2026-11-12 的验收记录写明三份计划开发完成、463 项自动化测试通过、构建正常；这是当时的开发验证记录。真实 DSH 宿主走查与 Grok Bot 联调未完成，最终可用性仍需负责人按清单验收。
